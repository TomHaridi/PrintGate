# 绑定码（扫码绑定管理员）爆破可行性评估

测试对象：PrintGate v2.1.0 `POST /api/mp/bind`（绑码提权为管理员）
测试方式：本地起真实实例（临时数据目录），脚本化模拟攻击者，逐项取证
脚本：`tools/bind-bruteforce-test.js`、`tools/bind-security-probe.js`、`tools/bind-proxy-probe.js`
测试时间：2026-10-24

---

## 一、结论（先说答案）

**爆破这条路走不通。** 绑定码是 128 位密码学随机数，且被三层机制夹住，没有任何已知手段能在有生之年撞中。

| 维度 | 实测结果 |
| --- | --- |
| 码空间 | `crypto.randomBytes(16).toString('hex')` → 32 hex = **128 bit**，与安装无关的随机值，非时间戳/自增 |
| 单 IP 尝试预算 | **5 次 / 15 分钟**（`loginMaxFail=5`，`loginLockMin=15`），锁定期内正确码也被拒 |
| 请求级限流 | `/mp/bind` 15 次/分钟；全局 `/api` 900 次/分钟（同 IP） |
| 比较方式 | `crypto.timingSafeEqual` + 长度校验，无用时侧信道；正确码/错误码返回同一句「绑定码不正确或已失效」 |
| 前置门槛 | 必须先拿到小程序登录态（`requireMiniUser`），匿名请求直接 401 |
| 穷举耗时 | 480 次/IP/天 → 撞中期望值 ≈ **1.9×10³³ 年 · IP**（宇宙年龄 1.4×10¹⁰ 年） |
| 单次命中概率 | 一个 IP 打满一年 ≈ 1.4×10⁻³⁶ |

实测连击序列（干净实例）：`1:403 2:403 3:403 4:403 5:403 6:429/LOCKED …`，第 6 次起被锁 15 分钟；换另一个用户的正确码同样 429 —— 锁是 IP 维度、跨用户共享，锁生效在正确码路径上也验证过。

输入边界也干净：空串/超短/4096 超长/大小写变体/尾部 NUL/`{$ne:null}` 对象注入/Base64 变形全部 403。`[token]` 数组会被 `String()` 展平后命中（仅因校验用 `String()`，无注入面，不算漏洞）。尾部空格因 `.trim()` 被接受，无影响。

## 二、但发现 3 个真实缺陷（与爆破无关，风险更高）

### 🔴 P1 绑定码永不过期、成功一次也不作废（可无限次提权）

代码里只有「重新生成」会换码，`/api/mp/bind` 成功后**不清除 `bindToken`**，也没有 TTL 字段。

实测：同一个码，用户 A 绑定成功后，用户 B 拿同一个码再次绑定 → `status=200 绑定成功，你现在是管理员`。

影响：一次泄漏（截图外发、投屏演示、远程协助、客服代看后台、浏览器历史/截图群文件）就等于**永久管理员后门**，且攻击者提权后可以把码再发给别人批量提权。这是本次评估里唯一「实际可利用」的问题。

`GET /api/admin/bind/info` 返回字段只有 `ok/token/qr`，**没有任何 `expiresAt`**。

### 🟠 P2 任意登录用户都能尝试绑定，绕过审批

`/mp/bind` 只挂了 `requireMiniUser`（仅拦 `blocked`），没挂 `requireApprovedUser`。实测 `pending`（待审批）用户拿正确码 → 直接 `ok=true role=admin status=approved`。

设计上「有码即为管理员」可以接受，但它意味着：**审批开关对新用户毫无防护意义**——只要码泄漏，任何扫过小程序的人都能从 pending 一步跳到 approved admin。

### 🟡 P3 限流是 per-IP，两个场景会失效

1. **IPv6 换源地址**：单机拿到一个 /64 就有 2⁶⁴ 个源地址，每个地址一份独立配额，per-IP 锁形同虚设。当前没有全局/账号维度配额（`login_attempts` 按 ip 计数，无 `LIMIT` 的全局失败计数）。
2. **`TRUST_PROXY=true` 且公网直连**：实测把 X-Forwarded-For 每次换一个 IP，连打 10 次**全部 403，零拦截**，随后正确码 `200` 提权成功。此时 `clientIp` 取 XFF 最后一跳 = 攻击者自填值，登录锁定/全局限流/审计 IP 一起失效（审计里记的全是伪造 IP，取证也被污染）。

`DEPLOY.txt` 已写明「公网直连时千万不要开这个开关」，但代码层没有任何兜底——一旦误开就是全线失守，值得加一道运行时防护（例如：来源不是内网/回环时，若带 XFF 则判定为可疑并忽略该头 + 告警）。

### 轻微

- `bindToken` 为空时返回 400「后台尚未生成绑定码」，其余返回 403，可探测「是否已生成过码」；实际信息价值极低。
- 爆破会留痕：每次失败写 `audit(mp_bind_fail, ip)`，可在「审计日志」按此 action 告警。但 P3-2 场景下 IP 可伪造，告警可信度下降。

## 三、建议修复（按优先级）

| 优先级 | 改动 | 说明 |
| --- | --- | --- |
| P1-a | 绑定码加 TTL（如 10 分钟）+ 前端倒计时、自动轮换 | 页面本来就是「生成即有」的即时操作，10 分钟足够扫 |
| P1-b | 绑定成功后立即作废并返回新码 | UX 上后台页面自动刷新出新码；要绑第二个微信就再扫一次新的 |
| P2 | `/mp/bind` 追加 `requireApprovedUser` 之外的显式校验 | 或明确保留「有码即授权」，但要在页面上写清楚该码等价于管理员密钥 |
| P3-1 | 加「全局失败计数 + 指数退避」或按 `kind` 的全局阈值告警 | 不必阻断，先做到「30 分钟内全站 >100 次 bind 失败 → 强制轮换绑定码 + 告警」 |
| P3-2 | 启动时若 `TRUST_PROXY=true` 且检测到直连（首个请求来自公网）→ 打印显著告警并忽略 XFF | 或改为只信任固定 hop 数 |

其中 P1-a/P1-b 是产品语义变更（一码一人 vs 一码多人），需要先定策略再动代码。

## 五、修复落地（v2.1.1）

按「一码一人 + TTL」策略完成修复，回归 15/15 通过（`tools/bind-token-policy-test.js`）。

| 问题 | 修复 |
| --- | --- |
| P1 码永不过期、可反复使用 | 新码带 `bindTokenExpiresAt`；`/mp/bind` 成功后立即 `rotateBindToken()`，响应带 `tokenRotated`；读取侧 `bindTokenInfo()` 发现过期就地换新。TTL 默认 10 分钟，`BIND_TOKEN_TTL_MIN` 可调 |
| P2 待审用户凭码直达 admin | 保持「有码即授权」的产品语义（这正是该功能用途），风险窗口由 TTL + 一次性收敛到 10 分钟内单次 |
| P3-1 分布式撞码无全局上限 | 全站 30 分钟内失败达 `BIND_FAIL_ROTATE`（默认 50）即强制换码，正在爆破的旧码当场作废；每次失败仍写 `audit(mp_bind_fail)` |
| P3-2 `TRUST_PROXY=true` + 公网直连可伪造 XFF | `clientIp()` 增加对端校验：socket 对端是公网地址时忽略 XFF，直接用真实对端记账；反代同机（127.0.0.1）/同内网（10./172./192.168.）才采信。单测覆盖 5 种组合 |
| 输入面 | `verifyBindToken()` 先按 `^[0-9a-f]{32}$` 卡格式，再 `timingSafeEqual`；`[token]` 数组展平的路子一并堵掉 |

前端 `Wechat.vue`：绑定卡片显示 `mm:ss` 倒计时（末段转黄），归零或被人用掉后 10 秒轮询自动换新码并提示。

### 仍然保留的设计取舍

- 绑定码在有效期内可用于**任意**登录用户（不要求 approved），因为该功能本身就是把待审批用户升为管理员；安全边界靠「码是 128 位随机 + 10 分钟 + 一次性」。
- per-IP 限流对 IPv6 换源无效的问题仍在（未加全局硬上限，只做失败阈值换码 + 审计），因为加全局硬限流会误伤正常审批。
