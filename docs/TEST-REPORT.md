## 二·补六、第八轮：打印机历史清理（手动 + 自动）

磁盘被 `data/spool/`、`uploads/`、`scans/` 和任务记录撑满，但旧的保留期清理只按固定策略跑，  
用户在打印机页看不到"到底占了多少、现在能不能清"。这一轮把清理做成可见、可控、可自动。

### 新增能力

| 项    | 说明                                                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 统计   | `GET /api/printers/history` 返回任务（总量/已完成/进行中）、CUPS 已完成作业数、落盘文件数与体积、源文件与扫描件数与体积、上次清理记录                                                |
| 手动清理 | `POST /api/printers/history/clean`，五类范围（`tasks` / `cups` / `spool` / `files` / `scans`）+ 保留天数 0–3650（0 表示全部），限流 12 次/分，返回各项移除数与释放体积 |
| 安全边界 | 只删已结束任务；被未完成任务引用的源文件自动跳过；CUPS 用 `cancel -x` 清理并尊重保留天数                                                                               |
| 自动清理 | 开关 + 保留天数存进设置（`autoCleanHistory` / `historyDays`），后台每 `PG_AUTO_CLEAN_MS`（默认 1 小时）跑一次，写 `auto_cleanup` 审计                            |
| UI   | 打印机页右上角「历史清理」：四项统计卡片、范围复选框、保留天数下拉、立即清理、自动清理开关，清理后提示"释放 X MB/KB/B"                                                                   |

### 修掉的三个 bug

1. **CUPS 清理无视保留天数**：`cleanCups()` 拿到截止时间却没用，选「保留最近 30 天」也会把队列清空 → 改为按 `days > 0` 过滤 `CompletedTime`。
2. **自动清理忽略 `historyDays`**：`autoRun()` 只清了任务和落盘，CUPS 走默认清空，与用户设置不符 → 统一传 `days`。
3. **"释放 0.0 MB" 文案**：小于 1 MB 时一律显示 MB，造成"清了但没释放"的误解 → 按 KB/MB 自适应。

### 部署踩坑（已写进 DEPLOY.txt）

镜像重建时 Docker 复用了旧的前端构建层，`/app/public/assets` 仍是上一版，

## 二·补七、第九轮：深度猎杀（两种生成内容注入）

前八轮都是"功能有没有做对"，这一轮换了视角：**用户可控的数据流到哪里、有没有被当成代码/配置执行**。  
新写了 `tools/bug-hunt3.js`（59 项），围绕配置注入、令牌安全、参数模糊、并发一致性与权限纵深。

### 漏洞 1：frpc.toml 配置注入（高危）

`buildFrpToml()` 直接把 `frpServer` / `frpToken` 插值进 TOML 字符串，而这两个字段在  
`PUT /api/settings` 里几乎没有校验（服务端只 `trim().slice(128)`，Token 连长度都不限）。

```js
`auth.token = "${c.frpToken}"`     // 用户可控值直接进引号
```

实测把 Token 置为 `evil"` + 换行 + `[[proxies]] ...`，落盘配置真的多出一个代理节点：

```
auth.token = "evil"
[[proxies]]
name = "injected"
localIP = "127.0.0.1"
localPort = 9091
remotePort = 19999
```

后果是**把容器内任意端口经 frps 转发到公网**（frp 的 `remotePort` 本来就是干这个的），  
即一次完整的配置注入 → 内网暴露。

修复（两道防线）：

| 层    | 位置                   | 做法                                                                                       |
| ---- | -------------------- | ---------------------------------------------------------------------------------------- |
| 输入校验 | `routes/settings.js` | `frpServer` 限定 IP 或域名、≤128；`frpToken` 限 `[A-Za-z0-9._~+/-]`、≤256；`relayPublicUrl` 禁空白与引号 |
| 输出转义 | `system.js`          | 新增 `tomlStr()`，对 `\` `"` 与全部控制字符按 TOML basic string 转义，写入前一律经过它                          |

### 漏洞 2：审计导出 CSV 公式注入（中危）

`/api/audit/export` 只对 `detail` 列转义双引号，既没有给其余列加保护，也没防 Excel 公式前缀。  
而多条审计会**原样记录文件名**（`file_delete` 的 detail 就是文件名，`upload`、`mp_upload` 同理）。

实测四种公式串都能完整入库并出现在导出里：

```
"879","admin","file_delete","=1+1.pdf",...
"873","admin","file_delete","@SUM(1+9).pdf",...
```

管理员用 Excel / WPS 打开导出的 CSV 即触发公式执行，可用于钓鱼或数据外泄。

修复：新增 `csvCell()`，所有列统一走它 —— 先对 `= + - @` 及 `\t \r` 开头的值前置单引号中和，再做双引号转义。

### 顺带加固

- JWT：`verify()` 显式锁定 `algorithms: ['HS256']`。原实现虽已能挡住 `alg: none`（实测 401），  
  但不指定算法等于把安全性押在库默认值上。
- 中转页「对外访问地址 BASE」改为 `disabled`：该字段与「小程序对接」页共用同一个存储项，  
  两处都能编辑会互相覆盖。

### 本轮结论：没有问题的地方

排查后确认安全的，一并记录避免重复劳动：

- **命令注入**：所有外部命令走 `execFile(cmd, args)` 数组传参，全仓无 `exec()` 拼接（`db.exec`、`re.exec` 除外）；
- **打印参数**：`normalizeOptions()` 的白名单足够严，`pageRanges` 正则、`extra` 正则、`SAFE_TOKEN` 都在生效，  
  注入串只能被丢弃或规范化，队列里查不到残留；
- **越权纵深**：`/api/mp/*` 每次请求都实时查 `users` 表，拉黑/删除用户的旧 JWT 立即失效；  
  `requireAdmin` 校验 scope + 会话纪元；小程序令牌访问 `/api/users`、`/api/settings`、`/api/keys`、  
  `/api/audit`、`/api/security/attempts` 全部 401；
- **令牌伪造**：`alg: none`、篡改 payload、空/垃圾令牌均为 401；
- **并发**：同一任务并发取消的结果一致（一个 200 + 其余 409），并发删除文件幂等。

### 技术选型（为什么这么做）

- **中文字体**：镜像原本只有 12 个拉丁字体，中文会印成方块。加入 `font-wqy-zenhei`，  
  但它只有 TTC 集合、pdfkit 不能直读；构建期用 `fontforge` 拆出单个 TTF 到  
  `/usr/share/fonts/printgate/wqy-zenhei.ttf` 后立刻 `apk del fontforge`，运行镜像只多约 11 MB。
- **水印叠加**：没在 Node 里逐页合并，而是 `qpdf --overlay in.pdf out.pdf --overlay wm.pdf --repeat=1-z --`  
  一次铺完，稳定且不改变原文档结构（文字层保留）。

### 本轮修掉的问题

1. **标签不显示**：`n-tab-pane` 在只做标签、不承载内容（自闭合）时，标签文字渲染为空 —— 页面上只剩一条空白圆角条。  
   改用 `n-tab` 后又发现 `#tab` 插槽同样不生效（回退显示 name，出现 `standard/text/invoice/idcard`）。  
   最终改为自绘分段标签，样式与参考图一致且完全可控。
2. **水印对非 PDF 静默失效**：`executeTask` 原先只处理 `.pdf`，图片和 TXT 即使勾了水印也不会印出来，  
   用户只会看到"设了没效果"。现在图片先用 pdfkit 包成单页 PDF、TXT 先排版成 PDF，再统一叠加。
3. **纸张被驱动值覆盖**：详情加载时用 `lpoptions` 的当前值回填 `opt.media`，  
   导致用户选的 A4 在刷新后被改成 Letter。改为只把驱动能力用于下拉项，不覆盖用户选择。
4. **移动端 4 个标签挤成一行**：窄屏改 2×2 排布。

## 二·补九、第十一轮：扫码登录专项验证

针对「登录页扫码登录」做了一次端到端、带边界的验证，新增 `tools/qr-login-test.js`。

### 覆盖的链路

票据状态机 `pending → scanned → confirmed → 一次性签发后台令牌`：

| 环节  | 验证点                                                       | 结果 |
| --- | --------------------------------------------------------- | -- |
| 前置  | 关闭开关时创建码 403；未配 AppID 时 400；开启后返回 ticket/qr/expiresIn=120 | 通过 |
| 权限  | 非管理员扫码 403、非管理员确认 403，且被拒后票据仍为 pending（不误标 scanned）       | 通过 |
| 状态  | 管理员扫码 → 网页轮询到 scanned → 确认 → 轮询拿到 token 且令牌可访问后台          | 通过 |
| 一次性 | 二次轮询返回 expired，不再签发令牌                                     | 通过 |
| 异常  | 伪造/空票据 404；小程序接口未登录 401；过期票据状态 expired、扫码提示过期、确认 404      | 通过 |
| 限流  | 创建二维码每分钟 30 次，实测第 28 次开始 429                              | 通过 |

### 修掉的两个真实问题

1. **切回密码登录后仍在轮询**（真 bug）：`watch(tab)` 只在切到扫码页时启动轮询，切走不停。  
   实测切回密码页后每 2 秒还在请求 `/auth/qr/status`，最多空转约 55 次，白耗请求并吃掉 `qrpoll` 限流额度。  
   修复：抽出 `stopPolling()`，切走即停、切回恢复，组件卸载复用同一逻辑。  
   顺带把轮询失败从"静默忽略"改为连续 3 次失败提示「网络异常，正在重试…」，避免用户对着断线的二维码干等。
2. **未配置小程序时扫码页一直转圈**（UI 死角）：全新实例上 `qrLoginEnabled=true` 但还没填 AppID，  
   `/auth/qr/create` 返回 400，前端 `qrData` 为空 → 页面上只剩一个永远转的 `n-spin`，没有任何解释。  
   修复：依据 `store.boot.wxConfigured` 分支渲染，未配置时直接给出「扫码登录暂不可用 + 去哪里配置」的提示，  
   并且 `watch` 里也不再触发无意义的创建请求。

### 14.5 给运维的结论

1. **必须挂卷**：`docker run -v printgate-data:/data` 或 `docker compose`（compose 里已配 `./data:/data`）。不挂卷时删容器 = 数据全丢。
2. **打印机队列现在会自愈**，但 `CUPS` 本体状态（`/etc/cups`）建议按 compose 里的 `./cups:/etc/cups` 挂出来，双保险。
3. **备份**：优雅 `docker stop` 之后只拷 `data/printgate.db` 即可（已自动 checkpoint）；若不确定是否优雅停止，把 `printgate.db`、`-wal`、`-shm` 三个一起拷。
4. **崩溃后**可能有任务被标成「服务重启导致打印作业丢失」——这是**故意**的，请让用户重打，而不是让系统假装打过了。

## 第二十一轮：身份证「一键矫正识别切割」+「实时拼接预览 / 大小方向调节」（v2.1.0）

### 21.1 两个需求

1. **一键自动矫正识别切割**：随手拍的歪斜证件，点一下自动找出身份证、旋转摆正并裁掉背景。
2. **上传后实时生成打印拼接预览**：正反两面拼成一张 A4 的实时预览，可分别调整**大小（缩放）/ 方向（旋转）**。

### 21.2 实现

- 新增 `server/src/idcard.js`：纯 `sharp`（新增依赖，含 linuxmusl-arm64 预编译）+ 自研算法，不依赖 OpenCV/ImageMagick：
  - 缩略灰度 → Otsu 二值化（亮/暗两种极性都试）→ 形态学**闭运算**（膨胀→腐蚀）填掉卡片内部文字/人像的洞 → 连通域取面积最大、宽高比最接近身份证(≈1.586)的区域 → 前景像素 **PCA** 求主轴倾斜角；
  - **两步法摆正**：先 `rotate(-倾斜角)` 整图摆正（背景用图像边缘均值填充避免黑边干扰），再二次检测取精确轴对齐框，内缩去毛刺后 extract；
  - 关键坑：首检时卡片倾斜大，轴对齐框宽高比会失真（45° 时接近 1.0），所以首检放宽比例范围只做「定位+估角」，二检摆正后再用严格比例取框。
- 后端路由：
  - `POST /api/print/idcard/auto-crop`（识别+矫正，落库为新 PNG 文件）；
  - `POST /api/print/idcard/preview`（正反拼接，返回第一页 PNG，实时预览）；
  - `POST /api/print/idcard`（提交打印，与预览同一套参数）。
  - `render.idcardPdf`：pdfkit 里 `translate` 到槽位中心 + `rotate` + 居中缩放画图，每面独立 `rotate(0/90/180/270)` / `scale(0.3~3)`，正反各占半页、带裁切虚线。
- 前端 `Print.vue` 身份证模式：新增「一键矫正识别切割」按钮；每面各一组「旋转 + 缩放」控件；上传/调参后防抖 250ms 实时重排预览，提交走 `/print/idcard`。

## 第二十二轮：绑定码加固 + 普通用户门户与角色隔离（v2.2.0）

### 22.1 背景

用户提出两个诉求：一是确认「扫码绑定管理员的绑定码能否被爆破」，二是「登录页要区分普通用户与管理员，  
普通用户只能打印/看自己的记录/清空历史，管理员能一键拉黑并隐藏普通用户的详细设置，还要能关掉密码登录」。

### 22.2 绑定码安全评估（结论：不可爆破）

- 码为 `crypto.randomBytes(16).toString('hex')` = **128 bit**，非时间戳/自增。
- 单 IP 预算 5 次 / 15 分钟（`loginMaxFail=5`、`loginLockMin=15`），实测 `1~5:403 → 6:429/LOCKED`；锁定期内带正确码同样 429。
- `timingSafeEqual` + 长度校验，错误码与过期码返回同一句，无侧信道；匿名请求 401；XFF 伪装在 `TRUST_PROXY=false` 下无效。
- 穷举期望 ≈ 1.9×10³³ 年·IP（480 次/天）。

### 22.3 顺带修掉的真实缺陷

| 问题                                             | 修复                                                                                           |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 绑定码永不过期、成功后不作废（同一码可反复给多人提权，已实测复现）              | 一码一人 + TTL 10 分钟（`BIND_TOKEN_TTL_MIN`），绑定成功/到期即换新；全站 30 分钟内失败达 `BIND_FAIL_ROTATE`（默认 50）强制换码 |
| `TRUST_PROXY=true` 且公网直连时可伪造 XFF（实测 10/10 零拦截） | `clientIp()` 校验 socket 对端：公网地址时忽略 XFF；反代同机/同内网才采信                                            |
| 登录页提示「删库重置密码」                                  | 按用户要求删除该段文案                                                                                  |

### 22.4 普通用户门户与角色隔离

- 扫码登录按角色签发不同会话：管理员 `scope=admin`（管理台），普通用户 `scope=miniapp`（门户）。  
  `/api/auth/whoami` 供前端分流，普通用户会被路由强制拉回 `/portal`。
- 门户能力：上传 → 选打印机 → 打印、查看自己的记录、**一键清空自己的历史**（只清已结束任务与自己的文件，  
  进行中的任务不动，且不误删他人文件）。管理接口对普通用户一律 401/403。
- 管理端：一键拉黑（拉黑后 `whoami` 与扫码立即 403）、`隐藏普通用户详细设置` 开关（门户与小程序里只剩  
  文件/打印机，参数固定单份/黑白/单面/A4）、`允许管理员密码登录` 开关（与扫码不能同时关，服务端强校验）。

1. 「最新镜像里没有普通用户注册按钮」——网页登录页只有密码/扫码两个 Tab，新用户不知道账号从哪来

  SPA 内退出到登录页不会重新拉取，于是仍渲染密码 Tab，填密码只会收到 403。

### 29.1 背景

## 第三十一轮：恢复 frp（改用官方新版）+ 崩溃自愈（v2.4.3）

### 31.1 线上 502 的真正原因

`relay.jddgz.top` 返回 `502 Bad Gateway`（nginx），而我的中转自检截图显示：  
本机服务正常、打印机就绪、**frp 客户端二进制「未包含 frpc」**、服务端可达。

结论：**v2.4.2 为了消 CVE 把 frp 整个移除了，导致 frpc 隧道起不来，云端 nginx 没有上游 → 502。**  
这是我上一轮"减攻击面"的改动踩了实际业务，属于决策失误，本轮修正。

### 31.2 修法：装官方新版，而不是删掉

Alpine 仓库的 frp 停在 **0.65.0**（内嵌 `x/crypto 0.37`、`x/net 0.39`，正是那批 9 个 critical 的来源）；  
官方最新已是 **0.71.1**（2026-10-14），这些模块已升级。

因此改为：

```dockerfile
ARG WITH_FRP=1          # 默认恢复安装
ARG FRP_VERSION=0.71.1  # 从 GitHub release 取官方二进制
ARG TARGETARCH          # 多架构自动选 linux_arm64 / linux_amd64
```

- 不再 `apk add frp`，改为下载官方 tar.gz 只取 `frpc`（约 20MB），装完删临时文件

## 第三十七轮：修小程序换头像 + 全量验证（v2.4.9）

### 37.1 换头像的根因

微信 `chooseAvatar` 给的临时文件名**经常没有扩展名**（或直接叫 `file`）。旧实现按 `originalname` 猜扩展名：

```js
const ext = path.extname(file.originalname) || '.png'   // ← 猜错
```

于是 JPEG 被存成 `.png`，读取接口又按扩展名回 `Content-Type: image/png`，  
**MIME 与实际内容不符** → 小程序 `<image>` 解码失败，表现就是「点了更换没反应 / 头像裂图」。

### 37.2 修法

- 上传先落**无扩展名随机名**，再按**文件头**判定真实类型（PNG/JPEG/GIF/WEBP），改名后落库
- 读取接口兼容无扩展名文件：按内容兜底给 `Content-Type`，命中不了才算 404
- 小程序侧 `avatarOf()` 统一拼 URL：绝对地址直接用、相对路径补 baseUrl、去掉 baseUrl 末尾多余斜杠（避免 `http://host//api/...`）

| `.png` 名 + PNG    | 200 ✅                       |

## 第三十九轮：修复小程序「保存到相册」失败（v5.9）

## 第四十三轮：网络一体机扫描修复（v2.4.12）

### 43.1 真实根因：airscan 后端从来没装上

`sane-airscan` 依赖 `libtiff.so.6` 与 `libxml2.so.2`，`node:22-alpine` 里没有这两个运行时库：

```
ERROR: unable to select packages:
  so:libtiff.so.6 (no such package): required by sane-airscan
  so:libxml2.so.2 (no such package): required by sane-airscan
```

而旧 Dockerfile 写的是：

```dockerfile
RUN apk add sane-airscan || echo "装不上就跳过"
```

**失败被 `|| echo` 吞掉了** —— 镜像构建"成功"，但里面根本没有 airscan 后端，
所以网络一体机永远 `scanimage -L` 看不到。另外 `sane-network` 在这个 Alpine 版本里根本不存在。

修复：

```dockerfile
ARG WITH_AIRSCAN=1
RUN apk add tiff libxml2 \
 && (apk add sane-airscan || (echo '构建失败…' && exit 1)) \
 && (ls /usr/lib/sane/ | grep -qi airscan || (echo 'airscan 未落盘' && exit 1))
```
- 先补 `tiff` `libxml2` 两个运行时依赖
- 装不上就**构建失败**（不再静默），确实不需要时用 `--build-arg WITH_AIRSCAN=0`
- 构建末尾校验 `/usr/lib/sane/libsane-airscan.so` 存在

### 43.2 新增：不依赖 mDNS 的接入方式

桥接网络下 mDNS 广播过不来，自动发现必然失败。现在有两条路：

| 方式 | 适用 | 做法 |
| --- | --- | --- |
| A. 手填 IP（新增） | 任何平台，桥接网络也行 | 「扫描仪 → 网络扫描仪」填 IP → 探测 → 添加 |
| B. host 网络 | 仅 Linux | `network_mode: host`，同网段自动发现 |

新增能力：
- `GET/POST/DELETE /api/scanners/network` + `POST /api/scanners/network/probe`
- 探测走 `GET http://<ip>/eSCL/ScannerCapabilities`（兼容 `/ScannerCapabilities`），解析 `pwg:MakeAndModel`
- 配置写到 `/data/sane.d/airscan.conf`（**数据卷，重建不丢**），格式：`"名称" = http://ip:port`
- `SANE_CONFIG_DIR=/data/sane.d:/etc/sane.d`：airscan 用我们的配置，epson2 等仍用系统配置
- `cupsEnv()` 每次现读该变量，避免 ENV 快照丢失
- 诊断接口补 `airscan`（配置路径 + 已配设备）与 `network`（网卡/IP/是否桥接）
- 网络模式判断改用 `/sys/class/net/eth0/{iflink,ifindex}` 比对（桥接时两者不等），非 Linux 才退回网段猜测

## 第四十四轮：网络探测加固 + Office 转换默认内置（v2.4.13）

### 44.1 探测失败不一定是不能扫

用户看到「这个地址没有响应 eSCL 扫描接口」，但旧探测只看两个路径、只走 http、4 秒超时、且把 401 当失败。
真实一体机的差异很大：路径可能在 `/eSCL`、端口可能在 8080、可能只开 HTTPS、可能需要认证、老机型甚至只支持 WSD。

重写 `probeNetwork`：

## 第四十六轮：扫描「Error during device I/O」（v2.4.15）

### 46.1 现象与根因

设备能列出来，但一点「开始扫描」就报：

```
scanimage: open of device airscan:e0:1 failed: Error during device I/O
```

这句是 **airscan 打开了 TCP 连接但握手失败**，和设备名无关。三种最常见成因：

| 成因 | 判断依据 |
| --- | --- |
| mDNS 发现来的地址是**主机名**，容器解析不了 | 设备名是 `airscan:e0:<数字>`（自动发现），不是手填的名字 |
| 一体机被别的客户端占用（厂商「扫描到计算机」/手机 App 预览中） | 同一时刻其它设备能扫，这台不行 |
| 设备休眠 / 刚开机 | 等几秒重试就成功 |

### 46.2 修法

1. **错误文案**：把 I/O 错误翻成上面三条可执行建议（原来只有"扫描失败"）
2. **自动重试一次**：命中 I/O 错误时等 1.5 秒重试，覆盖"刚唤醒"场景
3. **设备自检接口** `GET /api/scanners/:device/selftest`
   - `scanimage --test`：只打开设备读参数、不真正扫描 → 区分"打不开"和"参数不对"
   - `airscan-discover`：列出设备真实地址，一眼看出是 IP 还是主机名
   - `scanimage -A`：读参数是否正常（顺带确认设备可用）
4. **设备下拉显示地址**：`airscan` 设备自动补 `url`，地址是主机名时标注「容器可能解析不了 → 建议手填 IP」
5. **前端**：扫描失败处加「设备自检」按钮，展示「能否打开 / 结论 / 发现到的地址 / 原始输出」

### 46.3 验证

- 错误翻译 5 个分支单测全过（I/O、权限、忙、参数、超时）
- 自检接口（无水机环境）：`noBinary=true` + 明确提示"未安装 sane"，不会把锅甩给设备
- 回归：376 项，0 失败

### 46.4 现场怎么处理（给用户）

1. 点「设备自检」，看 `发现到的地址` 是 `http://192.168.x.x` 还是主机名
2. 若是主机名 → 在「网络扫描仪」里手填 IP 添加，用新设备扫
3. 若是 IP → 关掉打印机上的「扫描到计算机」、手机扫描 App，等 10 秒重试
4. 仍失败 → 浏览器打开 `http://IP/eSCL/ScannerStatus`，能返回 XML 说明设备在线，问题在参数/占用

## 第五十轮：安装进度条 + 换镜像免重装 + 镜像瘦身（v2.4.19）

三个诉求：① 装 Office 要有进度条；② 换镜像后不用再装一遍；③ 在功能不减的前提下把镜像压小。

### 50.1 进度条（真实推进，不是假动画）

`server/src/converter.js` 拆三段：**下载 0-40% → 安装 40-92% → 校验 92-100%**。

| 依据 | 做法 |
| --- | --- |
| 下载阶段的百分比 | `apk fetch` 各版本输出格式不一，改为盯数据卷里 `.apk` 文件数量，每 800ms 采样；总数取 `apk fetch -R --simulate` 的预估值与实际下到数的较大值 |
| 下载阶段封顶 39% | simulate 只列直接依赖，实际会拉传递依赖，包数会一路上涨；把百分比锁死会在中途倒退，干脆封顶等安装阶段给真数 |
| 安装阶段 | 解析 `apk` 的 `(n/m) Installing …` 行，得到真实的包序号 |
| 前端 | `Settings.vue` 轮询 `/settings/office/status`，显示阶段文字（正在下载/安装/校验）、`已下载 n/total`、`已用 xx 秒` |

### 50.2 换镜像不用重装（数据卷缓存 + 启动自动恢复）

装在容器可写层的东西，一换镜像就没了。现在把安装包缓存到数据卷：

```
/data/office/pkgs/*.apk     # apk fetch -R 下来的全部包
/data/office/meta.json      # 安装时间、包列表、版本
```

- **安装时**：先 `apk fetch -R -o /data/office/pkgs` 全量下载，再从本地包 `apk add --allow-untrusted` 安装（离线可重复）
- **换镜像启动时**：`index.js` 调 `converter.restoreIfCached()`，发现 `soffice` 不在但数据卷有缓存 → 后台自动离线装回去，用户不用点任何按钮，日志里能看到 `office: 正在从数据卷恢复 Office 组件（151 个包）`
- **释放空间**：`DELETE /settings/office/cache` + 界面「清理缓存」

### 50.3 实测中抓到的真 bug：装完转换直接 abort

进度条与持久化都跑通了，但**顺手验证「装好的 Office 真能转 PDF」时炸了**：

```
$ docker exec pg-office2 soffice --headless --convert-to pdf t.txt
terminate called after throwing an instance of 'com::sun::star::uno::RuntimeException'
RC=134          # 没有产出 t.pdf
```

根因链（三个问题叠在一起，少一个都发现不了）：

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **`apk fetch` 15 分钟硬超时** | `cups.run(..., { timeout: 900000 })`。这台机器下载 151 个包刚好用掉 ~919 秒，**fetch 被 kill** |
| 2 | 中断后仍当成功 | 只判断「目标目录有没有 .apk」——依赖包已下到 151 个，于是继续装；`libreoffice-writer` / `impress` 两个主包**根本没下到** |
| 3 | 校验只看 `which soffice` | 只装了 calc 也有 soffice 二进制，`available=true`，一转换就 abort |

实测证据：数据卷里只有 `libreoffice-calc-*.apk`，`apk list --installed | grep libreoffice` 只有 calc/common/lang 三个；手工补装 writer/impress 后同一条命令立刻成功：

```
convert /tmp/t.txt as a Writer document -> /tmp/t.pdf using filter : writer_pdf_Export
-rw-r--r-- 14593 Oct 29 21:22 /tmp/t.pdf
```

修复（都在 `converter.js`）：

- fetch 超时 15 分钟 → **60 分钟**
- 新增 `remotePkgNames()`：用 `apk fetch -R --simulate` 取**完整包清单（含传递依赖）**，缓存是否可用只看「清单里每个包的文件在不在」，不再数文件个数
- 新增 `cacheMissingNames()` + 逐个补齐：缺几个就下几个，**补缺刻意不带 `-R`**（带了会把已有的 151 个依赖重下一遍，实测白等十几分钟）
- 缺得少（≤5 个）直接逐个补，缺得多（首次安装）才整包 `apk fetch -R`
- 安装前主包缺件 → 直接失败并说明缺哪个，不再拿残件往下装
- 校验从 `which soffice` 升级为 `apk info -e <pkg>` 三个主包逐一确认（`missingInstalled()`），缺一个就判失败
- `restoreIfCached()` 用完整清单判断缓存，残缺就**拒绝自动恢复**并提示点「一键安装」补齐
- 状态接口新增 `cache.missingMain`；「一键安装」文案按缺包情况区分

### 50.4 第二次踩坑：缓存缺 libreoffice-common 会让 apk 回滚、进度条倒退

补上 writer/impress 后再装，进度到 **91%（221/225）突然掉回 63%（101/225）**——`apk add` 失败后整体回滚，前端进度条跟着倒退。

原因：缓存的 151 个包里有依赖、有 calc，但**缺 395MB 的 `libreoffice-common`**（第一次 fetch 被超时掐断时它还没轮到）。`apk add` 装到 writer 时发现缺依赖，转去联网拉 common，网络一抖就整批回滚。

这正是「只数文件个数」判不出问题的场景，所以改成按完整包清单校验（见 50.3 的 `remotePkgNames()`）。修复后：缓存缺 3 个包 → 只下这 3 个（writer 4.7MB / impress 0.4MB / common），下载阶段 40 秒完成，进度条不再倒退。

### 50.5 第三个坑：`apk fetch --simulate` 的输出不是纯包名

完整性清单靠解析 `apk fetch -R --simulate` 的输出，而它印的是 **`Downloading alsa-lib-1.2.15.3-r0`**。第一版正则要求「行首就是包名」，结果一行都匹配不上 → 清单为空 → 完整性判断静默失效，界面照样报「已找到 153 个安装包」。现在用 `pkgNameOf()` 去掉 `Downloading ` 前缀再匹配，并补了 7 条样例断言（含 `ca-certificates-bundle-20261020-r0`、`boost1.84-iostreams-1.84.0-r6` 这类带点号的版本）。

另外补了离线兜底：`requiredNames()` 先问仓库，拿不到（离线）就用 `meta.json` 里上次记下的 `names` 清单，否则离线恢复会因为「没有清单」而误判缓存完整。装成功后会后台 `backfillCache()` 把缺的包（典型就是 395MB 的 common）补进数据卷，保证下一次换镜像真的能离线恢复。

## 第五十二轮：普通用户上传图片失败（真机临时文件名没有扩展名）（v2.4.21 / 小程序 v5.14）

报障：**管理员能上传打印图片，普通用户上传图片不成功**。

### 52.1 复现（先证明不是权限问题）

本地起服务，造一个已审批的普通用户，按真机的三种文件名形态各传一次同样内容的 PNG：

| 用例 | 结果 |
| --- | --- |
| 未审批用户上传 | 403「账号待管理员授权」← 这是设计行为，不是 bug |
| 已审批 + 文件名 `tmp_abc.jpg` | **400「文件内容与扩展名不符（.jpg）」** |
| 已审批 + 文件名 `tmp_abc`（无扩展名） | **400「不支持的文件类型」** |
| 已审批 + 无扩展名 + 无展示名 | **400「不支持的文件类型」** |

根因清楚了：**`registerFile` 只按扩展名判类型**，而微信真机 `chooseMedia` / `chooseMessageFile` 给出的临时路径经常是 `tmp_xxxx` 这种**没有扩展名**的（Android 尤其明显），于是 `extOf()` 返回 null，直接被拒。

管理员为什么没事：管理员基本在**后台网页**上传，浏览器带原始文件名（有扩展名）；小程序端才走临时路径。

同一个坑还有第二个面：相册里 `.jpg` 后缀实际是 PNG 的情况不少，扩展名和内容不一致会被「内容与扩展名不符」误杀。

### 52.2 修法

**后端 `registerFile()` 改为内容优先**：

- 新增 `sniffExt(path)`：读文件头认出 `.pdf / .png / .jpg / .gif / .bmp / .webp / .tiff`
- 图片和 PDF **一律以文件头为准**（`CONTENT_FIRST_EXT`）：没扩展名就按内容补，扩展名和内容不符就按内容纠正
- Office（docx/xlsx/pptx 是 ZIP 容器）光看魔数分不出来，仍按扩展名走，`contentMatches()` 的老校验保留
- 展示名：优先用端上带的 `filename`，扩展名强制换成真实类型；没带就用原文件名，超长再退回 stem
- 拒绝提示补上具体扩展名（原来「不支持的文件类型 」后面是空的）

**小程序端**：`app.json` 加 `networkTimeout.uploadFile: 180000` —— 手机原图动辄 5-10MB，默认 60 秒在弱网下会超时，表现同样是「上传失败」。

## 第五十三轮：上传成功但打不开 —— 磁盘文件名还是 .bin

### 53.1 现象

普通用户「已经授权过了」，传图片仍然失败；管理员在后台网页传同一张图却正常。

### 53.2 根因（比 2.4.21 更深一层）

2.4.21 修的是**校验**：按文件头认类型，无扩展名的图片不再被 400 拦掉。但 `multer` 落盘时是按
「上传时文件名的扩展名」命名的：

```js
// server/src/routes/print.js  storage.filename
const ext = extOf(file.originalname) || '.bin';   // 微信真机给的是 tmp_xxxx → 没有扩展名
cb(null, `${ts}${rand}${ext}`);                    // → 落成 xxxxxxxx.bin
```

`registerFile` 事后嗅探出 `.png` 只改了**数据库里的展示名**，磁盘文件依然叫 `.bin`。而下游全部按
`storage_path` 的后缀判类型：

| 位置 | 判断 | `.bin` 的后果 |
| --- | --- | --- |
| `POST /mp/files/merge` | `MERGE_IMG_EXT.includes(extOf(storage_path))` | 400「不是图片，不能和其它图片合并」← 多选打印必挂 |
| `GET /files/:id/preview` | `IMAGE_EXT.includes(ext)` | 不走原图直出，改去当 PDF 渲染 → 报错 |
| `POST /print`（图片合排） | `render.readableImage()` 要求 `.jpg/.png` 结尾 | 「格式无法解析」 |

管理员走的是后台网页，浏览器 `FormData` 带原始文件名（`IMG_1234.jpg`），落盘就是 `.jpg`，
所以从来没踩到 —— 这就是「管理员能传、普通用户不能」的真正分界。

### 53.3 修复

1. `registerFile`：嗅探出真实类型后**把磁盘文件改名**，保持名实一致（`xxxx.bin` → `xxxx.png`）
2. `merge`：扩展名不像图片时再用文件头确认一次，兼容修复前已落盘的 `.bin`
3. `IMAGE_EXT` 补 `.webp / .heic / .heif`；`sniffExt` 增加 HEIC 识别（ISO BMFF `ftyp` + brand）
4. 新增 `server/src/legacyfix.js`：启动时扫库里 `storage_path LIKE '%.bin'` 的活跃文件，
   按文件头改名并更新 DB —— 之前传过的图不用重传，预览立刻可用
5. 小程序端：上传/合成失败改用 `wx.showModal` 展示完整原因，并带上 HTTP 状态码
   （`Toast` 会截断长文案，真机上「上传失败」四个字定位不了问题）

### 58.2 素材问题与处理

设计稿是 985×903 的 **JPG**，网格三通道、无 alpha、背景是深青渐变，白圈离边很近。

## 第五十九轮：把小程序搬到 iOS —— H5 + WKWebView 壳

### 59.1 先定结论（能力边界）

iOS 的 `.app` 只能由 **macOS + Xcode** 编译。本机是 Windows，实测无 `xcodebuild`、无 CocoaPods，
所以「在这台机器上直接产出 IPA」不成立 —— 这不是配置问题。

可行的最小代价路线：把**除编译外的所有事情做完**，编译交给 macOS（GitHub Actions 免费 runner）。

同时必须先解决一个产品级问题：小程序依赖 `wx.login`（openid）与 `wx.chooseMessageFile`，
这两个在原生 App 里没有等价物。查代码发现后端早有账号体系：
`POST /api/auth/account/login` 的注释写着「与小程序同一套会话：门户用的 /api/mp/* 接口认这个令牌」，
`sec.signUser()` 里 `scope: 'miniapp'`。**因此只要用账号密码登录，整套 `/api/mp/*` 可直接复用，无需改后端。**

### 59.2 架构

```
iPhone App (Swift + WKWebView)
  └── http(s)://<服务器>/m/        ← 新增：移动端 H5，服务端自带，与接口同源
        └── /api/mp/*             ← 与小程序完全同一套接口
```

选 WebView 而不是把 UI 编译进 App 的三个理由：
1. 界面与打印逻辑都在服务端，**改 UI 只更新镜像**，App 不必重签（自签 7 天到期很痛）
2. 同源加载，没有 CORS、没有跨域 Cookie
3. 文件选择/拍照走系统控件，体验与原生一致
